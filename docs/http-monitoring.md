# HTTP/HTTPS Traffic Monitoring

## 1. Objective

The objective of this project was to build a monitoring environment capable of collecting and analyzing HTTP/HTTPS traffic from a Windows endpoint.<br>
I used mitmproxy to inspect web traffic and Python to extract relevant information into structured logs.<br>

The goal was to explore how HTTP/HTTPS traffic data could complement endpoint telemetry and support security investigations.

## 2. Environment

The lab environment consisted of the following components:

- **Operating System:** Windows 11
- **HTTP/HTTPS Proxy:** mitmproxy (mitmweb)
- **Log Processing:** Python
- **Log Format:** JSON Lines (JSONL)

## 3. Implementation

### 3.1 Lab Architecture

I configured mitmproxy as a local HTTP/HTTPS proxy to capture web traffic generated by the Windows endpoint.

The basic data flow was:

**Windows Applications → mitmproxy → Python Add-on → JSONL Logs**

This approach allowed me to collect HTTP/HTTPS request and response metadata in a structured format for further analysis.

### 3.2 mitmproxy Setup

I downloaded and installed mitmproxy on Windows from the [official mitmproxy download page](https://www.mitmproxy.org/downloads/) and configured a local proxy listener.

The proxy was configured to listen on `127.0.0.1:8080`, while the mitmweb interface was accessible through port `8081`.

To inspect HTTPS traffic, I installed the mitmproxy certificate authority (CA) certificate into the Windows trusted root certificate store.

This enabled mitmproxy to decrypt and inspect HTTPS traffic from applications that used the configured proxy and trusted the certificate.

### 3.3 HTTP/HTTPS Log Collection

To start HTTP/HTTPS traffic collection, I launched mitmweb with two custom Python add-ons using the following PowerShell command:

```powershell
mitmweb `
  --listen-host 127.0.0.1 `
  --listen-port 8080 `
  --set web_host=127.0.0.1 `
  --set web_port=8081 `
  -s ".\scripts\logger.py" `
  -s ".\scripts\flow_cleanup.py"
```

I also enabled the manual proxy configuration in Windows and set the proxy address to `127.0.0.1` and the port to `8080`.

I developed a custom Python add-on, [logger.py](../scripts/logger.py), to extract HTTP/HTTPS traffic information and write it to JSONL files.

The collected data includes various fields that may be useful for future security detection and analysis.

Some examples of the collected fields are:

- Client IP address
- Request URL
- Destination hostname
- HTTP request method
- HTTP response status code
- HTTP Referer
- User-Agent

These fields were selected to provide useful context for identifying suspicious HTTP/HTTPS activity and developing detection rules.

Using JSONL made the collected data easier to process programmatically and integrate with other monitoring components.

### 3.4 Log Management

To support continuous traffic collection, I implemented mechanisms to manage disk usage and memory consumption.

I implemented log rotation to prevent traffic log files from growing indefinitely. The rotation configuration was designed to limit the size and number of retained log files.

In addition, I developed a custom Python add-on, [flow_cleanup.py](../scripts/flow_cleanup.py), to periodically clear traffic flows retained in mitmproxy's memory and reduce memory usage.

These mechanisms help maintain a manageable monitoring environment during continuous traffic collection.

### 3.5 Integration with Splunk

I configured Splunk Universal Forwarder on the Windows endpoint to monitor the JSONL log file generated by mitmproxy and forward the collected events to Splunk Enterprise.

I added the following configuration to `inputs.conf`:

```ini
[monitor://<PROJECT_PATH>\log_monitor_lab\logs\mitmproxy.jsonl]
disabled = 0
index = proxy
sourcetype = http:mitmproxy
```

**Note:** Replace `<PROJECT_PATH>` with the appropriate local directory path before applying this configuration.

This configuration enables Universal Forwarder to monitor the JSONL file and send newly collected events to the `proxy` index in Splunk Enterprise using the `http:mitmproxy` sourcetype.

This allows HTTP/HTTPS traffic logs to be searched and analyzed alongside Sysmon endpoint events within a single monitoring platform.

In Splunk Enterprise, I verified that the mitmproxy logs were successfully ingested and could be searched.

## 4. Findings and Lessons Learned

### 4.1 HTTP/HTTPS Traffic Visibility

This project demonstrated how a local HTTP/HTTPS proxy can provide visibility into web requests and responses beyond basic network connection metadata.

While Sysmon provides endpoint-level information, such as process creation and network connections, mitmproxy provides more detailed application-layer information, including requested URLs, destination hostnames, HTTP methods, and response status codes.

However, I learned that mitmproxy's visibility depends on whether applications use the configured proxy and whether HTTPS interception is supported.

Therefore, proxy-based monitoring should be considered a complementary data source rather than a complete record of all endpoint network activity.

### 4.2 HTTPS Traffic Inspection

Inspecting HTTPS traffic required additional configuration, including installing the mitmproxy CA certificate into the Windows trusted root certificate store.

Through this process, I learned that configuring a proxy alone is not sufficient to inspect encrypted HTTPS traffic. Applications must also trust the CA certificate used by mitmproxy, and some applications may not support HTTPS interception.

This highlighted the importance of understanding certificate trust and application compatibility when implementing HTTPS monitoring.

### 4.3 Log and Resource Management

Continuous HTTP/HTTPS traffic collection can generate a large volume of log data and increase memory consumption.

To address these challenges, I implemented log rotation to manage disk usage and a custom Python add-on to periodically clear traffic flows retained in mitmproxy's memory.

Through this experience, I learned that effective monitoring requires not only collecting useful security data but also managing the resources consumed by the monitoring system.

I also recognized the importance of selecting relevant fields based on detection objectives rather than collecting unnecessary information.

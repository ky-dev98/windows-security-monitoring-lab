# HTTP/HTTPS Traffic Monitoring

## 1. Objective

The objective of this project was to build a monitoring environment capable of collecting and analyzing HTTP/HTTPS traffic from a Windows endpoint.<br>
I used mitmproxy to inspect web traffic and Python to extract relevant information into structured logs.<br>

The goal was to explore how HTTP/HTTPS traffic data could complement endpoint telemetry and support security investigations.

## 2. Environment

The lab environment consisted of the following components:

- **Operating System:** Windows 11
- **HTTP/HTTPS Proxy:** mitmproxy (mitmweb)
- **Log Processing:** Python
- **Log Format:** JSON Lines (JSONL)

## 3. Implementation

### 3.1 Lab Architecture

I configured mitmproxy as a local HTTP/HTTPS proxy to capture web traffic generated by the Windows endpoint.

The basic data flow was:

**Windows Applications → mitmproxy → Python Add-on → JSONL Logs**

This approach allowed me to collect HTTP/HTTPS request and response metadata in a structured format for further analysis.

### 3.2 mitmproxy Setup

I installed mitmproxy on Windows and configured a local proxy listener.

The proxy was configured to listen on `127.0.0.1:8080`, while the mitmweb interface was accessible through port `8081`.<br>
To inspect HTTPS traffic, I installed the mitmproxy certificate authority (CA) certificate into the Windows trusted root certificate store.<br>

This enabled mitmproxy to decrypt and inspect HTTPS traffic from applications that used the configured proxy and trusted the certificate.

### 3.3 HTTP/HTTPS Log Collection

I developed a Python add-on for mitmproxy to extract HTTP/HTTPS traffic information and write it to JSONL files.

The collected information included:

- Request URL
- Destination hostname
- HTTP request method
- HTTP response status code

Using JSONL made the collected data easier to process programmatically and integrate with other monitoring components.

### 3.4 Log Management

I implemented log rotation to prevent traffic logs from growing indefinitely.

The rotation configuration was designed to limit the size and number of retained log files.

This was important for maintaining a manageable monitoring environment during continuous traffic collection.

### 3.5 Integration with Security Monitoring

I explored how HTTP/HTTPS traffic logs could be used alongside Sysmon endpoint events.

Sysmon provides endpoint-level information, such as process creation and network connections, while mitmproxy provides application-layer HTTP/HTTPS information.

Combining these data sources can provide additional context for investigating suspicious activity.

## 4. Findings

This project demonstrated how a local HTTP/HTTPS proxy can provide visibility into web requests and responses that is not available from network connection metadata alone.

In particular, structured HTTP/HTTPS logs can provide useful information such as destination hostnames, requested URLs, and HTTP response status codes.

However, the visibility provided by mitmproxy depends on whether applications use the configured proxy and whether HTTPS interception is supported.

Therefore, proxy-based monitoring should be considered a complementary data source rather than a complete record of all endpoint network activity.

## 5. Challenges and Lessons Learned

### 5.1 Challenges

**HTTPS Traffic Inspection**

Inspecting HTTPS traffic required additional configuration, including installing and trusting the mitmproxy CA certificate.

I learned that configuring a proxy alone is not sufficient to inspect encrypted HTTPS traffic.

**Managing Log Volume**

Collecting HTTP/HTTPS traffic can generate a large amount of log data.

This made it important to consider log rotation and the selection of information necessary for security analysis.

### 5.2 Lessons Learned

Through this project, I learned that different monitoring technologies provide different levels of visibility.

While Sysmon can capture endpoint activity and network connection metadata, mitmproxy can provide more detailed HTTP/HTTPS information.

I also recognized that collecting detailed traffic data introduces operational considerations, including certificate management, application compatibility, and log storage.

This experience reinforced the importance of selecting appropriate data sources based on monitoring objectives rather than relying on a single monitoring tool.
